# Tower Lock Failover (v0.1.18+)

- Route: `/cellular/cell-locking/tower-locking`. Components (U4.17, RM520N canon): `components/cellular/tower-locking/{tower-locking,live-strip,automation-tiles,persist-toggle,settings-write,schedule-tile,lte-tower-card,nr-sa-tower-card,shapes}`; failover and the schedule live in the "Lock automation" section, not on a leg card, because the failover releases both radios. Keep-after-reboot is per radio (`AT+QNWLOCK="save_ctrl",<lte>,<nr>` takes them separately): each leg card owns a hover-reveal `lock_clock` toggle at the right of its footer, beside Lock / Remove lock (both primary), reading `modem_state.persist_lte` / `persist_nr`; `settings.sh` accepts `persist_lte` / `persist_nr` and re-sends the other radio's live value, and a failover save sends no persist field at all (`settings-write.ts` is the shared write). Each leg card shows Remove lock while the saved lock is what the modem holds, Lock otherwise (both when the lock state is unreadable); Clear fields (footer left) and keep-after-reboot use the hover-reveal `components/ui/reveal-button.tsx`.
- **Contract**: LTE/NR-SA cell lock does NOT auto-enable Signal Failover — user must explicitly turn it on in the automation section (`automation-tiles.tsx`). Unlocking still auto-stops + auto-disables failover.
- Default: `TOWER_DEFAULT_CONFIG.failover.enabled = false`. Existing configs preserved by `tower_config_init` on upgrade.
- Install gating: `qmanager_tower_failover` in `UCI_GATED_SERVICES` (install.sh) — fresh install cannot auto-run; upgrade preserves prior symlink.
- **Unlock hardening**: init.d `stop` = SIGTERM → poll `is_daemon_pid_running` up to 2s via `sleep_fractional` (`usleep 100000` fallback to `sleep 1`) → `kill -9`. Always clears `$PID_FILE` + `$ACTIVATED_FLAG`, `return 0`.
- **Self-heal**: `failover_status.sh` (polled 3s) checks `.lte.enabled`/`.nr_sa.enabled`. Orphan watcher with no active lock → inline `stop` (NOT `disable` — preserve user's `failover.enabled` intent).
- **Spawn gating**: `tower_spawn_failover_watcher()` is the single choke point — early-returns `"false"` when `.failover.enabled != "true"`. All callers (`lock.sh`, `settings.sh`, `qmanager_tower_schedule`) go through it.
- **RSRP source in deep-idle**: `qmanager_tower_failover` reads `.lte.rsrp` / `.nr.rsrp` from `status.json`. These scalars come from `AT+QENG="servingcell"` (via `parse_serving_cell`), which the poller continues to run in the Adaptive Polling deep tier — it is the only AT command kept in that tier. RSRP may be up to one `deep_idle_interval` (default 60 s) stale when the UI is idle; this is the accepted staleness window. See [`docs/features/adaptive-polling.md`](../adaptive-polling.md) Invariant 7.
- Frontend: `use-tower-locking.ts::sendLockRequest` does NOT force `config.failover.enabled = true` from `data.failover_armed`. Config flows only from `fetchStatus()` / `updateSettings()`.
- UX hint: `automation-tiles.tsx` shows `automation.failover_hint` ("A lock is set, but failover is off. Locking never turns it on." in `public/locales/en/cellular.json`) when the failover chip reads `disabled` and the section is present (`presence === "present" && failState === "disabled"`).
- `settings.sh` disable-on-off + unlock-when-no-locks paths still run init.d `disable` (user intent). Band failover (`bands/lock.sh`) is out of scope — separate feature.
- **Both RATs must unlock**: the failover tracks `lte_ok` / `nr_ok` separately. An unlock counts only when `rc=0` and the reply carries no `ERROR`, and it can't be empty (an empty reply means a transport failure). A failed RAT is retried once after 5 s. Only when both succeed does the daemon write `enabled=false` for both, write the activated flag, and exit. Otherwise it clears only the RAT that did unlock in config, leaves the activated flag unwritten (its presence alone reads as "locks cleared"), resets `bad=0` and keeps watching. A single shared `ok` flag used to report COMPLETE with the LTE lock still applied.
- **Schedule results**: `qmanager_tower_schedule` judges each lock/unlock on `"$rc:$result"`, so a transport failure no longer flips config to `enabled:true` or spawns the watcher for a lock that never reached the modem.
- **Read confidence (U4.17, port of fork 786c366b)**: `status.sh` emits `modem_state.lte_read_ok` / `nr_read_ok` / `persist_read_ok` from each reader's rc. `status.sh` defaults `lte_locked` / `nr_locked` / `persist_*` to false before asking the modem, so without these flags a failed `AT+QNWLOCK` read looked like a confident "Unlocked" / "Disabled". The flags are optional and **absent means true** (a cached page can meet an older CGI): consumers test `=== false`, never `!== true`. `tower_read_nr_lock` now returns `error` + rc 1 when the reply has no `+QNWLOCK:` line (it used to answer `unlocked` + rc 0), matching the LTE and persist readers. `frequency/{lock,status}.sh` only match `locked*`, so they are unaffected.
- **Lock guard (U4.17)**: the hook blocks a second lock only while one is in flight (`lockInFlightRef`). The old guard blocked any lock while `watcher_running` was true, but the tower watcher is `while true` and runs for as long as a lock is active, so with failover on, re-targeting a locked leg was permanently blocked. Unlock always passes.
- **One-click tile actions**: each carrier tile in "Right now" (`live-strip.tsx`, `TileAction`) locks, adds or removes at once with no dialog. No lock on the radio: `lock_open` locks that cell. LTE already locked: the locked tile's filled `lock` removes just that cell (re-applies the remaining set, or unlocks when it was the last) and other LTE tiles show `add` (`lockLte([...held, cell])`, max 3). NR holds one cell, so another NR tile shows `lock_open` and replaces it. The cell set always comes from `modem_state.lte_cells`, never a leg card's draft slots, and re-applying is just `lock.sh` re-running `AT+QNWLOCK="common/4g",<n>,...` (no unlock first). The leg cards keep manual entry and their confirm dialog; the old tile-to-form prefill bus is gone. Unlock is never gated; lock is blocked with a reason on NSA / LTE-only or when LTE already holds 3 cells.
- **Hook results**: every mutator resolves `TowerActionResult { ok, error?, warning? }` with `error` already translated; `settings.sh`'s `persist_command_failed` comes back as `warning` (toast warns; config `persist` is not flipped). The fork's systemd-only `service_enable_failed` / `service_disable_failed` and the schedule `armed` field are deliberately not ported: this target uses procd + cron.
