# DPI Settings (Video Optimizer + Traffic Masquerade)

CGI: `network/video_optimizer.sh` · Hooks: `use-video-optimizer.ts`, `use-cdn-hostlist.ts`, `use-traffic-masquerade.ts` · Types: `video-optimizer.ts` · Reboot: No

- **Unified UI — "Traffic Engine".** Both modes share ONE page at `/local-network/traffic-engine` (a first-class Local Network sidebar entry, icon `MonitorPlay`). Since v2 the page is three cards with no tabs: the **Engine** card (mode switch, live packet chart, Bypass Hotspot) on top, then **Video Optimizer** and **Masquerade** side by side. `?mode=video|masquerade` scrolls to that card and highlights it for 1.6 s. Layout detail: "Frontend layout (v2)" below.
- Routes: canonical `/local-network/traffic-engine`. Old `/local-network/video-optimizer` → `…/traffic-engine`, `/local-network/traffic-masquerade` → `…/traffic-engine?mode=masquerade`, `/local-network/dpi-masking` → `…/traffic-engine` (all redirects).
- **Mutex is the mode switch.** The Engine card's 3-way `SegmentedField` (Off / Video Optimizer / Masquerade, a `Select` below the `sm` card width) expresses one-mode-at-a-time structurally; there is no takeover dialog. Picking a mode issues a single `saveSettings({enabled:true})` (the backend auto-disables the other mode on save, see below) and toasts. The composer holds a `pending` target until the polled status agrees, with an 8 s safety net, and after any save refreshes BOTH hooks (plus TTL and the hostlist). The packets/s figure and 60 s chart are derived client-side from per-poll `packets_processed` deltas; no new backend field.
- Binary: `nfqws` from zapret, installed to `/usr/bin/nfqws` on demand by `qmanager_dpi_install` (arch-detect → fetch `openwrt-embedded.tar.gz`). State files: `/tmp/qmanager_dpi_install.{json,pid}`.
- **The zapret release is pinned** (`ZAPRET_TAG` + `ZAPRET_SHA256` at the top of `qmanager_dpi_install`, currently v72.13). It downloads HTTPS-only from the fixed release URL (no GitHub API, no "latest"), and the sha256 must match before `tar` reads the archive; a mismatch or missing `sha256sum` fails closed. nfqws runs as root, so never relax this. To bump: take the `-openwrt-embedded.tar.gz` asset's `digest` from `gh api repos/bol-van/zapret/releases/tags/<tag>`, re-hash a download to confirm, and update both constants together.
- **Single shared nfqws on queue 200** — VO and masquerade are mutually exclusive modes of ONE process: single PID (`/var/run/nfqws.pid`). Backend enforces mutex in `save`/`save_masquerade`; init.d checks masquerade first, then VO.
- **procd writes `/var/run/nfqws.pid`** (`procd_set_param pidfile`). Do not `pidof` inside `start_service`: procd spawns the instance only after `start_service` returns, so the old `sleep 1; pidof nfqws > …` always wrote an empty file and `dpi_get_status` read `stopped` (uptime `0s`, `test_masquerade` refused "not running"). procd rewrites the file on every respawn, so its mtime (used by `dpi_get_uptime`) is the current process's start. `dpi_get_status` gates on `qm_read_pid "$NFQWS_PID" nfqws` (B5.11).
- **nft rules are persistent**, shipped as `/etc/nftables.d/12-mangle-qmanager-dpi.nft` (chain `mangle_postrouting_qmanager_dpi`, `oifname "rmnet*"`, `queue num 200 bypass`). fw4 sources the file on every load/reload, so rules survive `fw4 reload` (VPN toggles, port-forward edits, mwan3 ipset refreshes, etc. — all of which used to silently wipe the runtime-injected rules). The `bypass` flag means rules are safe to leave permanent even when nfqws is not running. The init.d script never touches nftables — it only manages the daemon. `dpi_helper.sh` no longer has `dpi_insert_rules` / `dpi_remove_rules`. Uninstall removes the .nft file and drops the live chain.
- Modes: VO = SNI split (`split2`) + QUIC desync, filtered by `--hostlist`. Masquerade = fake TLS ClientHello with spoofed SNI (default `speedtest.net`), all traffic.
- Hostlist: `/etc/qmanager/video_domains.txt` (active) + `video_domains_default.txt` (immutable). Hostlist CGI supports GET `?section=hostlist`, POST `save_hostlist`, POST `restore_hostlist`.
- GET handlers gate live stats on UCI `enabled` to avoid cross-mode contamination. Kernel check: `dpi_check_kmod()` reads `/proc/config.gz` for `CONFIG_NETFILTER_NETLINK_QUEUE=y`.
- Boot persistence: enabling either mode → init.d `enable`; disabling → `disable` only if BOTH are off. Uninstall always `disable`s.
- Deps: `libnetfilter-queue`, `libnfnetlink`, `libmnl`, full `curl`, NFQUEUE kernel support.
- **Bypass Hotspot row** (`bypass-hotspot-row.tsx`) is a friendly alias over the **global TTL/HL** state — NOT part of nfqws/the engine. It reuses `useTtlSettings` + `network/ttl.sh` (no new backend). The row is **presentational**: the `useTtlSettings` instance lives in the composer (`traffic-engine.tsx`) and is passed down as the `ttl` prop to the Engine card, which renders the row once. Owned in the composer so a refresh after a mode save reaches it, and `ttl.isLoading` is folded into the page's skeleton gate so its first load is covered too. Ownership is **value-based** because the canonical file `/etc/firewall.user.ttl` is written by both `ttl.sh` AND `qmanager_profile_apply` (a SIM profile's TTL shows up in the same global read, with no provenance marker): `0/0` → OFF + interactive (toggle on ⇒ `saveTtlHl(64,64)`); `64/64` → ON + interactive (toggle off ⇒ `saveTtlHl(0,0)`); any other active value → ON + **disabled** (external owner — TTL page or SIM profile — manage it there). i18n keys: `traffic_engine.bypass_*`.

## Frontend layout (v2)

Frontend only; no CGI contract changed. Class constants live in `components/local-network/traffic-engine/shapes.ts` and the loading skeletons read the same constants, so a skeleton cannot drift from the loaded card. Files: `traffic-engine.tsx` (composer), `engine-card.tsx`, `mode-card.tsx` (`VideoOptimizerCard`, `MasqueradeCard`, shared foot and check result), `hostnames-view.tsx`, `card-view.tsx` (in-card view header/body crossfade + Back), `packet-chart.tsx`, `handshake-strip.tsx`, `metric-row.tsx` (`MetricRow`, `DrillRow`), `check-row.tsx`, `bypass-hotspot-row.tsx`, `video-services.ts`, `engine-onboarding.tsx` + `result-alert.tsx` (not-installed state).

- **Engine card is the anchor.** Live view: the mode switch, Uptime / Packets handled / Package rows, Bypass Hotspot, and a 60 s packets/s area chart in uplink ink (null samples are gaps, y floor 500, live pulse on the last point). CardAction holds a chip only while it means something: `info` + spinner while starting, stopping, switching or applying, `success` while a mode runs, **nothing when idle**. The Package row drills into an in-card **Package** view (packet-queue support, engine, source, Remove behind a confirm; Remove is disabled while a mode runs). Missing packet-queue support disables the switch with a one-line reason and shows a page banner.
- **Mode cards** share one shell: a handshake strip ("What the carrier sees", fragments or decoys drawn in send order, a `Preview` tag while the draft differs from the saved value), Carrier reads / Acts on rows, the one setting (Desync Strength stepper, or disguise domain), the Verify Service / Test Injection check row (blocked with a reason while the mode is off), and a `CardFoot`. A running mode shows a `success` "Running" chip.
- **CardFoot Discard / Apply is back** (supersedes `720485b9`, which committed on blur). Strength and disguise domain are drafts; Apply commits them (restarting the engine briefly when that mode runs, otherwise the value rides along with the next enable, and Apply is blocked with a tooltip while the other mode owns the engine). Apply toasts, Discard does not. The mode switch and Bypass Hotspot still apply instantly and toast.
- **Feet never show the dirty state** (Card-Foot Apply Rule, `6b27ed2c`). A clean foot is empty; a dirty mode foot names only the consequence of applying (engine restarts briefly, takes effect on enable, or on switching); the Hostnames foot has no status at all. The slot and its `min-h-16` row stay so nothing jumps, and Apply/Save stays disabled while clean.
- **Hostnames view** opens in-card from the Video Optimizer "Acts on" row: add field on top, one column grouped by service under quiet labels with a muted `tabular-nums` count, **Custom** (domains the map does not know) first, 40 px rows in mono with an always-visible remove button, the list scrolling inside the card so the two mode cards stay equal height. Import / Export live in a `⋯` menu in CardAction next to Back; Restore defaults and Save sit in its own foot. While Masquerade owns the engine an `info` "Not in use" chip shows. Grouping comes from the static map in `video-services.ts`, built from the section comments in `scripts/etc/qmanager/video_domains_default.txt`; **edit both together** (each file says so).
- **No trailing ellipsis** on any label on this surface (busy states, Remove, Restore defaults, install steps; `engine-onboarding.tsx` strips one from backend step messages). This departs from PRODUCT.md Principle 7 (a trailing "…" means a dialog follows) for this page only.
- **Install** fires a success or error toast (id `traffic-engine-install`) when the polled install finishes.


### Hook result contract

`use-video-optimizer.ts`, `use-traffic-masquerade.ts` and `use-cdn-hostlist.ts` mutations (save, uninstall, hostlist save, restore defaults) return `MutationResult` (`types/mutation-result.ts`, `{ success, error }`). Handlers fire one `toast.success` or `toast.error` at the terminal moment and take the failure reason from the returned `error`, never from hook `error` state read after an `await` (Toast-Confirms Rule, [`docs/reference/toast-confirmation.md`](../reference/toast-confirmation.md)). Install and verify keep their polled `installResult` / `verifyResult` state.
